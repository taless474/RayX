# Experiment 06 — `--diag` decomposition of the high-lane FIFO-retire ceiling

## Purpose

Use the native HPX baseline's opt-in `--diag` mode to localize **where time is
spent** in the documented high-lane sleep-mode ceiling, and to test the existing
interpretation that the ~1390 req/s plateau is a **closed-loop FIFO-retire /
client-driver artifact** rather than HPX lane coordination.

This builds directly on
[experiments/02_variable_service_lane_sweep](../02_variable_service_lane_sweep/variable_service_lane_sweep.md)
(which first observed the ceiling) and
[experiments/04_hpx_native_multiclient](../04_hpx_native_multiclient/hpx_native_multiclient.md)
(which ruled out Python/GIL). Here we hold the workload fixed and vary only the
client retire discipline, then read the per-phase decomposition.

## Workload — the documented exp02 ceiling cell (fixed)

Every run uses the exact exp02 ceiling cell; **only `--retire-mode` varies**.

* `--service-pattern bimodal --service-low 1 --service-high 20 --service-p-high 0.1`
* `--seed 0`
* `--num-lanes 16 --concurrency 32`
* `--requests 1000 --warmup-requests 20`
* `--client-threads 1`
* `--hpx:threads=4`

No thread sweep. `--hpx:threads=4` is held so the numbers line up with the
documented exp02 cell.

## Retire modes compared

1. **`one_by_one`** — strict FIFO windowed retire (hold 32 in flight, retire the
   oldest, submit one). This is the ceiling case.
2. **`batch_wait --wait-batch 8`** — as-completed retire at the same in-flight
   window.
3. **`submit_all_get_all`** — **upper-bound / context only, NOT apples-to-apples**:
   it removes the fixed in-flight window entirely, so its latency phases are
   queue/bulk-drain shaped and must not be read as a like-for-like comparison.

Each mode is run **3 times**. Throughput is reported as the median (with
min/max); all per-phase, queue-depth, and lane numbers are taken from the
**representative repeat** = the run whose throughput is the median for that mode.

## Hypothesis

If the ceiling is a FIFO-retire / client-driver artifact (not HPX lane
coordination), then under `one_by_one`:

* the `completion` phase (`recv_ns − end_ns`, i.e. end-of-service → client
  observes it) should **dominate** total latency, while `service` stays near the
  bimodal mean and `pickup` (`start_ns − enqueue_ns`) stays small;
* lanes should be **under-utilized and evenly balanced** (starved of *retirement*,
  not of work), with trivial queue depth at enqueue;

and switching to `batch_wait` at the *same* window should **collapse
`completion`** and lift throughput while leaving `service` and per-lane work
essentially unchanged.

## Exact commands

Generated by `run_diag_ceiling.py` (see that file for the authoritative
template). For mode `M` with retire args `R` and repeat `r ∈ {1,2,3}`:

```text
hpx_impl/build/hpx_synthetic_baseline \
  --service-pattern bimodal --service-low 1 --service-high 20 \
  --service-p-high 0.1 --seed 0 \
  --num-lanes 16 --concurrency 32 --requests 1000 --warmup-requests 20 \
  --client-threads 1 --hpx:threads=4 \
  <R> \
  --out results/06_diag_fifo_ceiling/<M>_r<r>.jsonl \
  --diag --diag-out experiments/06_diag_fifo_ceiling_analysis/diag/<M>_r<r>.diag.json
```

with `<R>` being one of:

* `--retire-mode one_by_one`
* `--retire-mode batch_wait --wait-batch 8`
* `--retire-mode submit_all_get_all`

Reproduce all 9 runs + the reduction with:

```text
python experiments/06_diag_fifo_ceiling_analysis/run_diag_ceiling.py
```

## Results

### Throughput (req/s, median of 3; min–max)

| mode | median | min | max |
|---|---|---|---|
| `one_by_one` | 1391.5 | 1348.8 | 1421.8 |
| `batch_wait --wait-batch 8` | 2544.1 | 2492.9 | 2582.4 |
| `submit_all_get_all` *(context only)* | 2971.4 | 2924.4 | 2982.3 |

`batch_wait` lifts throughput **+82.8%** over `one_by_one` at the same in-flight

## Interpretation criteria → reading

* **Q1 — what dominates `one_by_one` latency?** `completion` (p50 20.9 ms),
  not `service` (p50 1.26 ms) and not `pickup` (p50 0.019 ms). The time is spent
  *after* service finishes, waiting to be retired by the client — i.e. on the
  driver retire path.
* **Q2 — how does `batch_wait` differ?** At the *same* window, `completion`
  collapses from 20.9 ms to **0.003 ms** p50 while `service` is unchanged
  (1.26 ms) and throughput rises +83%. The win comes entirely from removing the
  completion/retire wait, not from changing the work.
* **Q3 — do lanes/queue depth support the artifact reading?** Yes. Under
  `one_by_one` lanes are **under-utilized** (util median 0.26, max 0.48 — idle
  roughly half the time) and queue depth at enqueue is **~1** (no lane backlog),
  yet it is the slowest mode. Lanes had headroom and were evenly balanced
  (processed 62–63 across all 16). The throttle was the client retire discipline,
  not lane contention or coordination.

## Verdict — **SUPPORTS** the FIFO-retire / client-driver interpretation

The penalty in the ~1390 req/s ceiling is localized to the **`completion`
(client retire) phase**: it dominates under strict FIFO `one_by_one`, vanishes
under as-completed `batch_wait` at the same in-flight window with service and
per-lane work unchanged, and the lanes themselves are under-utilized with
near-zero enqueue backlog. This is consistent with short completed requests
sitting ready-but-unretired behind older in-flight 20 ms requests under strict
FIFO — a closed-loop client-driver effect, not HPX lane coordination.

### Surprising / noteworthy

* **`batch_wait` trades completion-wait for some pickup-wait.** Its `pickup`
  tail rises (p90 23.8 ms, p99 65.8 ms) because as-completed retirement lets the
  lane queue build modest depth (up to 16). It still nets a large win because the
  20+ ms `completion` wait is gone — but the head-of-line cost is relocated, not
  erased.
* **`submit_all_get_all` is dominated by both pickup and completion** (p50 89 ms
  / 244 ms) precisely because it removes the in-flight window and floods the
  lanes (queue depth p50 31, max 62). This is why it is labeled context-only: its
  latency phases are bulk-drain shaped and not comparable to the windowed modes.
* Lane `processed` is 62–63 across all 16 lanes in every mode, confirming the
  round-robin assignment is balanced and no lane is starved.

## Cautious-claim guardrail

This experiment **localizes the timing penalty to a phase bucket** (the client
`completion`/retire path) and shows the lanes stay busy-balanced with headroom.
It does **not** prove every possible system-level cause is excluded. It is a
single-machine, single-locality, synthetic **sleep-mode** workload at
`--hpx:threads=4` only; `submit_all_get_all` is upper-bound context, not a fair
comparison. The result is consistent with — and sharpens — the exp02/04
interpretation; it is not a general claim about HPX vs. any other runtime.
